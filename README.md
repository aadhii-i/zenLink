# zenLink

A production-grade, full-stack SaaS URL shortener — shorten links, brand them
with custom aliases, set expiry rules, and see exactly who's clicking what,
from where, and on what device.

> **Build status**: all 7 phases are complete — project foundation,
> authentication, URL shortening/redirects, the dashboard, analytics,
> security hardening, and testing/deployment. See
> [docs/SECURITY.md](./docs/SECURITY.md) for what's actually implemented/
> verified vs. known accepted risks (there's one — a `react-router-dom`
> advisory whose real fix needs a React 19 migration, documented there
> rather than silently ignored), and [docs/TESTING.md](./docs/TESTING.md)
> for an equally honest note on which test suite was actually executed
> (frontend) vs. written-and-syntax-checked-but-not-run (backend, which
> needs a real PostgreSQL this sandbox doesn't have).

## Architecture

The backend follows a **Clean Architecture / Service–Repository** layout so
business logic never depends on FastAPI or SQLAlchemy specifics directly:

```
Request → API (routers) → Service (business logic) → Repository (DB access) → Models
```

-   **`api/`** — HTTP layer only: request/response wiring, status codes, auth guards.
-   **`services/`** — business rules (e.g. "a custom alias must be unique",
    "an expired URL redirects nowhere"). No SQLAlchemy imports here.
-   **`repositories/`** — the only layer that talks to the database.
-   **`schemas/`** — Pydantic request/response models (never expose ORM models directly).
-   **`models/`** — SQLAlchemy ORM models.
-   **`core/`** — config, logging — cross-cutting concerns with no business logic.

## Getting Started

### Prerequisites

-   Docker & Docker Compose
-   (Optional, for running services outside Docker) Python 3.11+ and Node.js 20+

### Run with Docker (recommended)

```bash
cp .env.example .env
# Edit .env — at minimum change SECRET_KEY and POSTGRES_PASSWORD

docker-compose up --build
```

This starts four containers:

| Service  | URL                            |
| -------- | ------------------------------- |
| Frontend | http://localhost:5173           |
| Backend  | http://localhost:8000           |
| API Docs | http://localhost:8000/docs      |
| Postgres | localhost:5432                  |
| Redis    | localhost:6379                  |

On first boot, the backend container runs `alembic upgrade head` before
starting the API, so the database schema is always up to date automatically.

### Run without Docker (local dev)

**Backend:**

```bash
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # then point POSTGRES_HOST/REDIS_HOST at your local instances
alembic upgrade head
uvicorn app.main:app --reload
```

**Frontend:**

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

### Run in production mode

```bash
cp .env.example .env
# Fill in REAL values — docker-compose.prod.yml has no localhost
# fallbacks for SECRET_KEY, POSTGRES_PASSWORD, BASE_URL,
# BACKEND_CORS_ORIGINS, or VITE_API_URL on purpose.

docker compose -f docker-compose.prod.yml up -d --build
```

Builds the `production` target of each Dockerfile (no `--reload`, no bind
mounts, non-root backend user, frontend served as a static build via
nginx), and doesn't expose the Postgres/Redis ports to the host. It does
**not** bundle TLS termination or backups — see
[docs/DEPLOYMENT.md](./docs/DEPLOYMENT.md) for the full checklist and what's
intentionally left out.

## Testing

**Backend** (needs a real PostgreSQL + Redis — see
[docs/TESTING.md](./docs/TESTING.md)):

```bash
cd backend
pip install -r requirements-dev.txt
pytest -v
```

**Frontend:**

```bash
cd frontend
npm test
```

honest note on which suite was actually executed vs. written and
